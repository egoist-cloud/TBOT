# Quantum (TBOT)

Discord-бот клана: привязка Discord ↔ Steam, заявки с голосованием,
синхронизация ролей, RAG-ответы по правилам клана.

## Возможности

- **Привязка аккаунтов** Discord ↔ Steam через панель `cs2red`, проверка
  ролей клана, автосинхронизация по расписанию.
- **Заявки**: анкеты через модальное окно, публикация в канале заявок, в
  отдельной ветке и в лог-канале, кнопки «🙋 Взять», «Принять» (синяя) и
  «Отклонить» (красная). Достаточно одного голоса (`VOTES_REQUIRED=1`);
  при принятии автоматически выдаётся роль `ACCEPT_ROLE_ID`. Кнопки
  запретов — только в копии заявки в лог-канале. При отказе ветка
  архивируется и блокируется, но не удаляется.
- **Статистика модераторов**: `/status` показывает личные цифры по заявкам
  (принято / отклонено / в работе). Ответ всегда ephemeral — свои цифры
  видит только вызвавший, чужую статистику может посмотреть модератор.
- **ИИ**: ответы по правилам клана (`rules.txt`) с RAG-поиском по BM25,
  кэшем ответов и лимитом запросов на пользователя. Провайдеры:
  Gemini → OpenRouter → LLM7. У каждого своя переменная модели
  (`GEMINI_MODEL`, `OPENROUTER_MODEL`, `LLM7_MODEL`), поэтому каскад
  не ломается, если у одного провайдера нет ключа.
- **GitHub-синк**: данные хранятся в отдельном репозитории, поэтому
  привязки и базы не теряются при рестарте контейнера на Render.
- **Health-check** для Render по HTTP (`GET /` и `GET /health`).

## Запуск

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # Windows: copy .env.example .env
# заполни .env
python script.py
```

## Переменные окружения

Полный список — в [`.env.example`](.env.example). Важное:

| Переменная | Назначение |
|---|---|
| `DISCORD_TOKEN` | токен бота |
| `GUILD_ID` | ID сервера (без него команды не синхронизируются по guild) |
| `AUTO_ROLE_ID` | устаревшее; роль при принятии заявки теперь задаёт `ACCEPT_ROLE_ID` |
| `ACCEPT_ROLE_ID` | роль, выдаваемая автоматически при принятии заявки (по умолчанию `1448368118190837800`) |
| `ALLOWED_ROLE_ID`, `REVIEWER_ROLE_ID_2`, `EXTRA_REVIEWER_ROLE_1..3` | роли ревьюеров |
| `SPAM_VOTE_ROLE_ID` | роль, которой можно голосовать многократно |
| `VOTES_REQUIRED` | сколько голосов нужно для решения (по умолчанию 1) |
| `CS2RED_COOKIE_STRING` | админские cookie cs2red (или отдельные `CS2RED_*`) |
| `STEAM_API_KEY` | ключ Steam Web API |
| `GEMINI_API_KEY` / `OPENROUTER_API_KEY` / `LLM7_API_KEY` | ключи ИИ |
| `GEMINI_MODEL` | модель Gemini (по умолчанию `gemini-2.5-flash`; `gemini-1.5-*` удалены Google) |
| `OPENROUTER_MODEL` | модель OpenRouter (по умолчанию `gpt-4o-mini`) |
| `LLM7_MODEL` | селектор модели LLM7: `default` / `fast` / `pro` |
| `AI_MODEL` | устаревшая общая переменная; для Gemini используется как запасная, LLM7 игнорирует |
| `GITHUB_TOKEN`, `GITHUB_REPO`, `GITHUB_BRANCH` | синк данных с GitHub |
| `DATA_DIR` | папка с `quantum.db`, `rules.txt`, JSON-базами |
| `AGENT_CHANNEL_ID` | канал ИИ-агента (ошибки, отчёты, идеи) |
| `AGENT_CHECK_MINUTES` | период цикла наблюдения агента (по умолчанию 30) |
| `AGENT_HEALTH_INTERVAL_MINUTES` | как часто агент публикует отчёт о состоянии |
| `AGENT_IDEA_INTERVAL_MINUTES` | как часто агент публикует идею по улучшению |
| `APPLICATION_LOGS_CHANNEL_ID` | канал с копией заявок и кнопками запретов (по умолчанию `1511463623703265361`) |
| `TALENT_ROLE_ID` | роль клана TALENT для `/check`, `/check_all`, `/check_clan`, `/check_onlineall` (по умолчанию `1448368118190837800`) |
| `CHECK_ALL_DAYS` | глубина отчёта `/check_all` в днях (по умолчанию 14) |
| `ONLINE_MIN_HOURS` | минимальный недельный онлайн в часах для `/check_onlineall` (по умолчанию 9) |
| `HEALTH_CHECK_MINUTES` | период health-check (по умолчанию 15) |
| `DAILY_SUMMARY_HOUR` | час UTC ежедневной сводки (по умолчанию 9) |

Секреты (`CS2RED_*`, `STEAM_API_KEY`, `*_API_KEY`, `GITHUB_TOKEN`,
`DISCORD_TOKEN`) маскируются в логах и в `error_log.txt`.

## ИИ-агент (`quantum/agent.py`)

Наблюдатель за ботом, который пишет в служебный канал (`AGENT_CHANNEL_ID`):

- **ошибки команд** — сразу стильованным embed'ом «🚨 Ошибка в команде»;
- **отчёт о состоянии** — раз в `AGENT_HEALTH_INTERVAL_MINUTES`:
  аптайм, пинг, заявки, голоса, модераторы, статус ИИ, правил, GitHub и cs2red;
- **идея по улучшению** — раз в `AGENT_IDEA_INTERVAL_MINUTES`: ИИ-провайдера
  спрашивают напрямую (минуя RAG по правилам клана), ответ оформляется
  embed'ом «💡 Идея от ИИ-агента».

Последние 12 идей и расписание агента хранятся в таблице `meta`, поэтому
после перезапуска на Render агент не публикует отчёты пачкой.

## Команды

| Команда | Что делает |
|---|---|
| `/status` | профиль модератора: эффективность, разбивка по кланам, статус заявок и список заявок в работе (данные из таблицы `applications`). Ответ всегда ephemeral; чужую статистику видят только модераторы |
| `/admins` | кто администрирует клан: администраторы Discord, модераторы бота и ревьюерские роли (список кэшируется на минуту) |
| `/search` | история заявок игрока в клан: сводка (всего/принято/отклонено/в работе), разбивка по кланам и список заявок со статусом и `ticket-<message_id>`. Ответ всегда ephemeral; чужую историю видят только модераторы |
| `!setup_clan` (алиас `!setup`) | публикует в текущем канале официальные условия вступления (embed) и выпадающий список «Выберите клан» под ним — при выборе открывается модальное окно заявки. Текстовая команда, только для администраторов |
| `/check_mutes <steam_id>` | активные муты игрока на cs2red: тип, ник, причина, срок, дата и кто выдал. Если мутов нет — «✅ У игрока нет активных мутов». При 403/429 — «❌ Сайт cs2red временно недоступен» |
| `/check_bans <steam_id>` | активные баны и муты игрока на cs2red: тип, ник, причина, срок, даты блокировки/разблокировки и кто забанил. Если пусто — «✅ У игрока нет активных блокировок» |
| `/check` | прогоняет всех участников с ролью клана (`TALENT_ROLE_ID`, по умолчанию `1448368118190837800`; fallback — по имени `CLAN_NAME`) по cs2red и показывает сводку: сколько проверено, у кого есть активные блокировки, у кого нет привязки SteamID. Между игроками пауза 3 секунды, чтобы не получить 429. После проверки в лог-канал (`CHECK_LOG_CHANNEL_ID`, по умолчанию `1511463623703265361`) уходит мини-отчёт: кто получал мут/бан, когда, на какой срок, причина и кто выдал |
| `/check_all` | муты за `CHECK_ALL_DAYS` дней (по умолчанию 14) у всех участников с ролью TALENT. Ответ ephemeral, плюс мини-отчёт в лог-канал |
| `/check_onlineall` | недельный онлайн всех участников с ролью TALENT: для каждого берётся страница активности cs2red (текущая и прошлая неделя). Кто наиграл меньше `ONLINE_MIN_HOURS` (по умолчанию 9 ч.) — выводится отдельным полем «⚠️ Малоактивные». Ответ ephemeral + итог в лог-канал |
| `/activity <steam_id>` | активность одного игрока по SteamID64: время и наблюдатель за текущую/прошлую неделю, рассмотрено репортов. Ответ ephemeral |
| `/check_clan` | проверяет роли клана: у кого несколько ролей клана, у кого роль есть, но игрок не в клане, у кого в клане нет роли, кто без `/link`. Отчёт ephemeral + кнопка «🧹 Очистить лишние роли» (для администраторов) |
| `/clan_info` | профиль клана одним embed: состав на cs2red, число участников с ролью, сколько без `/link`, сколько подтверждено в клане. Ответ ephemeral |
| `/health` | полная проверка систем: Discord, права, cs2red, Steam, число записей в базах, фоновые задачи, каналы и ИИ-провайдеры. Публичный |

### Роли клана

Бот не только выдаёт роль клана, но и **снимает** её, когда игрок выходит
из клана или переходит в другой: cs2red перестаёт показывать его в составе
`/api/clans`, и роль удаляется. Синхронизация запускается:

- каждые `SYNC_INTERVAL_MINUTES` минут (по умолчанию 15) — задача `auto_sync`;
- раз в час — задача `hourly_clan_sync`.

Каждый запуск пишет в лог-канал, **что именно изменилось** и какие роли
снять не удалось. Полная таблица «кто в каком клане» больше не публикуется
каждые 15 минут: она делала два лишних запроса на каждого игрока и могла
приводить к блокировке cs2red (429). Частые причины, по которым
автоматическое снятие не срабатывает:

- роль бота стоит **ниже** роли клана — Discord запрещает управлять такими
  ролями. В лог придёт список таких ролей; поднимите роль бота в настройках
  сервера выше ролей клана;
- у участника нет привязки `/link` — автоматика не знает его SteamID и
  пропускает; такие участники тоже перечисляются в отчёте;
- `GUILD_ID` не задан на Render — фоновые задачи не находят сервер.

Роли, созданные ботом, запоминаются в `clan_roles.json`, а выданная роль
конкретному участнику — в `clan_members.json` (оба в `DATA_DIR`), поэтому
роль снимется даже если клан переименовали или он исчез из `/api/clans`.

### История заявок

В таблице `applications` хранится только **последняя** заявка игрока
(`user_id` — PRIMARY KEY). Полная история ведётся в отдельной таблице
`application_history`: новая запись появляется при каждой подаче заявки
(уникальность — по паре `user_id` + `app_id`), а финальный статус
(принята/отклонена) и решитель дописываются при закрытии заявки.
При первом запуске новой версии текущие заявки переносятся в историю
однократно (`INSERT OR IGNORE`).

## Безопасность

- HTTP-сессии разделены: админские cookie и заголовки `cs2red` уходят
  **только** на `cs2red.ru`. Steam, GitHub и LLM-провайдеры получают
  публичную сессию без cookie (`API.session` / `API.cs2red`).
- Хост определяется по hostname, а не по подстроке в URL.
- Панель управления (`/panel`) показывается только админу и только
  ephemeral-сообщением; каждая кнопка панели сама проверяет права.
- Голоса по заявке атомарны и привязаны к `app_id` заявки, а не к id
  сообщения: сообщение в канале и в ветке — одна запись голосов.
- Выбор клана в форме заявки отвечает модальным окном **первым** действием
  (Discord ждёт ответа 3 секунды — иначе «Приложение не ответило вовремя»,
  10062). View зарегистрирован как персистентный, поэтому опубликованное
  ранее сообщение со списком работает и после рестарта бота.
- Пустые или некорректные числовые переменные окружения не роняют бота на
  старте: значения читаются через `quantum.env.env_int` / `env_float`.

## Разработка и CI

```bash
pip install -r requirements.txt -r requirements-dev.txt
ruff check .
pytest -v
```

CI (`.github/workflows/ci.yml`) запускает `ruff` и `pytest` на Python 3.12
для `main`, `fix/**` и `feat/**`.

## Данные

Основное хранилище — SQLite (`quantum.db`, таблица `votes`, `applications`,
`links`, `players`, `users`, `moderators`, `seen`, `ai_cache`).
При первом запуске JSON-файлы (`links.json`, `players_db.json`,
`users_db.json`, `moderators.json`, `votes.json`, `seen.json`)
переносятся в SQLite и переименовываются в `*.bak`.
