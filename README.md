# Quantum (TBOT)

Discord-бот клана: привязка Discord ↔ Steam, заявки с голосованием,
синхронизация ролей, RAG-ответы по правилам клана.

## Возможности

- **Привязка аккаунтов** Discord ↔ Steam через панель `cs2red`, проверка
  ролей клана, автосинхронизация по расписанию.
- **Заявки**: анкеты через модальное окно, публикация в канале заявок и в
  отдельной ветке. В канале-логе кнопки «🙋 Взять» нет — она доступна
  только в ветке, созданной под заявку игрока; «Принять» (синяя) и
  «Отклонить» (красная) есть в обеих копиях. Достаточно одного голоса
  (`VOTES_REQUIRED=1`); при принятии автоматически выдаётся роль
  `ACCEPT_ROLE_ID`. Кнопки запретов — только в копии заявки в лог-канале.
  При отказе обязательно указывается причина (модальное окно «Причина
  отказа», минимум 3 символа): она сохраняется в заявке и истории, видна
  в `/check` и `/search`, попадает в аудит. После отказа модератора
  действует кулдаун `APPLICATION_REJECT_COOLDOWN_DAYS` (по умолчанию 3
  дня): игрок получает причину и дату следующей попытки, а форма заявки
  до этого срока не создаёт новую заявку. Кулдаун действует и после
  автоотклонения по TTL. Ветка архивируется и блокируется, но не удаляется.
- **Аудит действий**: привязки (`/link`, `/unlink`, `/admlink`), выдача и
  снятие прав (`/give`, `/take`), запреты, решения по заявкам и
  синхронизация ролей пишутся в append-only таблицу `audit_log` и
  дублируются embed'ом в канал `AUDIT_LOG_CHANNEL_ID`
  (по умолчанию `1555204495682568202`). Журнал смотрится командой
  `/audit` (только администраторы, ephemeral).
- **Статистика модераторов**: `/status` показывает личные цифры по заявкам
  (принято / отклонено / в работе), включая активные заявки, которые
  модератор взял кнопкой «Взять». Ответ всегда ephemeral — свои цифры
  видит только вызвавший, чужую статистику может посмотреть модератор.
- **ИИ**: ответы по правилам клана (`rules.txt`) с RAG-поиском по BM25,
  кэшем ответов и лимитом запросов на пользователя. Провайдеры:
  Gemini → Groq → Cerebras → Mistral → OpenRouter → NVIDIA → SambaNova →
  Cohere → HuggingFace → Cloudflare → LLM7 → Pollinations. GitHub
  Models исключён: сервис закрыт 30.07.2026. Последние два провайдера
  работают без ключа (анонимный бесплатный лимит), поэтому ИИ отвечает даже
  при пустом `.env`. У каждого провайдера своя переменная модели
  (`GEMINI_MODEL`, `OPENROUTER_MODEL`, `LLM7_MODEL` и т.д.). Префикс
  `models/` в `GEMINI_MODEL` срезается, при 404 модель выбирается через
  `ListModels`, а пауза после 429 берётся из `Retry-After` или из
  «retry in N seconds» в теле ответа.
- **Защита и скорость**: последовательные запросы к cs2red с настраиваемой
  паузой, короткий кэш профилей, «предохранитель» после 429/403/5xx
  (бот сразу отвечает, а не висит 5 минут) и `single_flight` для тяжёлых
  команд — `/check_all`, `/check_onlineall`, `/check_clan`, `/sync_all`,
  `/link_all`, `/auto_link` не запускаются параллельно.
- **GitHub-синк**: данные хранятся в отдельном репозитории, поэтому
  привязки и базы не теряются при рестарте контейнера на Render.
- **Health-check** для Render по HTTP (`GET /` и `GET /health`).
- **Preflight при старте**: проверяются `DISCORD_TOKEN` и `GUILD_ID` (без них
  процесс завершается с ошибкой), наличие служебных каналов, `Manage Roles`,
  права `View Channel` / `Send Messages` / `Embed Links` /
  `Read Message History`, доступ к SQLite, ключи и модели ИИ. Проблемы
  пишутся в лог и в канал ИИ-агента; если служебные каналы недоступны —
  владельцу сервера в ЛС. Успешная проверка выполняется один раз за запуск.
- **Один лидер фоновых задач**: инстансы делят lease в таблице `meta`
  (ключ `background_lease`, TTL 90 секунд, продление каждые 30 секунд).
  Только лидер запускает `auto_sync`, панели и остальные циклы; остальные
  остаются онлайн для команд и перехватывают lease, если лидер упал.
  Это работает, когда у инстансов общий `DATA_DIR`/`quantum.db`.
  Панели при старте и раз в час сверяются через общий реестр: дубли
  удаляются, пропавшая панель публикуется заново.

## Запуск

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # Windows: copy .env.example .env
# заполни .env
python script.py
```

## Запуск через Docker Compose

Нужен Docker с плагином Compose (`docker compose version`) и заполненный `.env`:
`docker-compose.yml` подключает его через `env_file` и без него не стартует.

```bash
cp .env.example .env            # Windows: copy .env.example .env
# заполнить минимум DISCORD_TOKEN и GUILD_ID

docker compose up -d --build    # собрать образ и запустить
docker compose logs -f bot      # логи, в том числе строки [seed]
docker compose ps               # STATUS: healthy, когда /health отвечает 200
docker compose down             # остановить; данные в volume остаются
docker compose down -v          # ВНИМАНИЕ: удаляет и volume с данными
```

Что важно знать:

- **Данные живут в именованном volume `quantum-data`** (`/data`, `DATA_DIR=/data`):
  `quantum.db`, `-wal`, `rules.txt`, `ai_training.json`, `error_log.txt`.
  Пересоздание контейнера и `down` базу не трогают, `down -v` — удаляет.
- **Порт 8080 — только для health-check** (`GET /` и `GET /health`). Discord
  работает через исходящий WebSocket, входящие порты боту не нужны.
- **Контейнер работает не от root** (пользователь `bot`, uid 1001). При первом
  подключении пустого volume Docker копирует в него `/data` из образа
  (`rules.txt`, `ai_training.json`) вместе с владельцем — руками `chown` делать
  не нужно.
- **`/health` отдаёт 503**, пока бот не залогинился (`is_ready()`) или уже
  закрывает соединение (`is_closed()`). Поэтому `healthy` в `docker compose ps`
  означает «бот реально в Discord», а не «процесс жив».
- **Обновление**: `git pull && docker compose up -d --build`. Миграции SQLite
  применяются на старте, volume сохраняется.
- **Если база не нужна** — контейнер можно запустить без `./seed` вообще:
  шаг импорта просто пропускается (см. ниже).

### Первый старт: что entrypoint делает с seed-файлами

`Dockerfile` ставит `ENTRYPOINT ["/usr/local/bin/docker-entrypoint.sh"]`, а
`CMD ["python", "script.py"]`. Скрипт делает ровно две вещи:

1. если каталог `${SEED_DIR:-/seed}` существует — запускает
   `python -m quantum.import_seed`;
2. дальше `exec "$@"`, то есть обычный запуск бота (`exec` важен: `python`
   становится PID 1, и SIGTERM от `docker stop` доходит до него).

`docker-compose.yml` монтирует `./seed` **только для чтения** в `/seed`
(`SEED_DIR=/seed`), поэтому в volume попадают только копии, а исходники на
хосте не меняются.

Что делает `quantum/import_seed.py`:

- **Копирует только недостающие файлы** из списка `links.json`,
  `players_db.json`, `moderators.json`, `users_db.json`, `votes.json`,
  `seen.json`. Если такой файл уже есть в `/data`, он **не перезаписывается**
  (там может лежать более свежая копия или `*.bak` после прошлого импорта).
- **Переносит JSON в SQLite** через `import_json_to_sqlite()`, после чего
  файлы переименовываются в `*.bak` (логика миграций — в
  `quantum/migrations.py`).
- **Ставит маркер `/data/.seed_imported`** — повторный рестарт контейнера
  видит его и ничего не делает (иначе каждый старт копировал бы и импортировал
  заново).
- **Не падает, если переносить нечего**: нет каталога `/seed`, он пуст или все
  файлы уже на месте — печатает `[seed] ...` и продолжает запуск.
- **Падает с кодом 1, если импорт сломался** — контейнер не стартует, чтобы не
  работать на полупустой базе. Ошибка видна в `docker compose logs bot`.

Повторить перенос принудительно (например, после ручной правки JSON):

```bash
# --entrypoint python: штатный entrypoint иначе запустит импорт второй раз
docker compose run --rm -e FORCE_SEED_IMPORT=1 --entrypoint python \
  bot -m quantum.import_seed
```

Нюанс с повтором: после успешного импорта файлы в `/data` переименованы в
`*.bak`, поэтому при следующем запуске они **снова** копируются из `./seed`
(под обычным именем их в `/data` уже нет, а `.bak` не трогается). А вот если
файл в `/data` остался под обычным именем, он не перезаписывается — удалите
его из volume, если нужна версия из `./seed`.

## Переменные окружения

Полный список — в [`.env.example`](.env.example). Важное:

| Переменная | Назначение |
|---|---|
| `DISCORD_TOKEN` | токен бота |
| `GUILD_ID` | ID сервера (без него команды не синхронизируются по guild) |
| `AUTO_ROLE_ID` | устаревшее; роль при принятии заявки теперь задаёт `ACCEPT_ROLE_ID` |
| `ACCEPT_ROLE_ID` | роль, выдаваемая автоматически при принятии заявки (по умолчанию `1448368118190837800`) |
| `ALLOWED_ROLE_ID`, `REVIEWER_ROLE_ID_2`, `EXTRA_REVIEWER_ROLE_1..3` | роли ревьюеров |
| `SPAM_VOTE_ROLE_ID` | роль, которой можно голосовать многократно |
| `VOTES_REQUIRED` | сколько голосов нужно для решения (по умолчанию 1) |
| `CS2RED_COOKIE_STRING` | админские cookie cs2red (или отдельные `CS2RED_*`) |
| `STEAM_API_KEY` | ключ Steam Web API |
| `GEMINI_API_KEY` / `OPENROUTER_API_KEY` / `LLM7_API_KEY` / `POLLINATIONS_API_KEY` | ключи ИИ (необязательны: LLM7 и Pollinations работают без ключа) |
| `GEMINI_MODEL` | модель Gemini (по умолчанию `gemini-flash-latest`; при 404 бот сам выбирает актуальную модель; префикс `models/` срезается) |
| `OPENROUTER_MODEL` | модель OpenRouter (по умолчанию `gpt-4o-mini`) |
| `LLM7_MODEL` | селектор модели LLM7: `default` / `fast` / `pro` |
| `POLLINATIONS_MODEL` | модель Pollinations (по умолчанию `openai-fast` — единственная на анонимном тире) |
| `AI_MODEL` | устаревшая общая переменная; для Gemini используется как запасная, LLM7 игнорирует |
| `GITHUB_TOKEN`, `GITHUB_REPO`, `GITHUB_BRANCH` | синк данных с GitHub |
| `DATA_DIR` | папка с `quantum.db`, `rules.txt`, JSON-базами |
| `AGENT_CHANNEL_ID` | канал ИИ-агента (ошибки, отчёты, идеи) |
| `AGENT_CHECK_MINUTES` | период цикла наблюдения агента (по умолчанию 30) |
| `AGENT_DIGEST_HOUR` | час UTC утреннего дайджеста агента (по умолчанию 9; `-1` — выключить) |
| `AGENT_IDEA_INTERVAL_MINUTES` | как часто агент публикует идею по улучшению |
| `APPLICATION_LOGS_CHANNEL_ID` | канал с копией заявок и кнопками запретов (по умолчанию `1511463623703265361`); «Взять» публикуется только в ветке заявки |
| `AUDIT_LOG_CHANNEL_ID` | канал аудита админских и модераторских действий (по умолчанию `1555204495682568202`) |
| `APPLICATION_REJECT_COOLDOWN_DAYS` | кулдаун повторной заявки после отказа, дни (по умолчанию 3; `0` — выключить) |
| `CLAN_PANEL_REFRESH_HOURS` | как часто пересоздавать панель заявки, часы (по умолчанию 20) |
| `CLAN_QUESTIONS_USER_ID` | пользователь для блока «По вопросам вступления» (приоритет над ролью) |
| `CLAN_QUESTIONS_ROLE_ID` | устаревший вариант: роль для того же блока, если пользователь не задан |
| `CS2RED_RATE_LIMIT_SECONDS` | пауза между запросами к cs2red, секунды (по умолчанию 2.5; ниже 1.5 повышает риск 429) |
| `CS2RED_BLOCK_BASE_SECONDS` | базовая пауза «предохранителя» после 429/403/5xx, секунды (по умолчанию 60) |
| `CS2RED_BLOCK_MAX_SECONDS` | максимальная пауза предохранителя, секунды (по умолчанию 1800) |
| `CS2RED_USER_CACHE_TTL` | время жизни кэша профиля игрока, секунды (по умолчанию 60) |
| `TALENT_ROLE_ID` | роль клана TALENT для `/check_all`, `/check_clan`, `/check_onlineall`, `/activity_week` (по умолчанию `1448368118190837800`) |
| `SITE_ROLE_AUDIT_HOURS` | период полного отчёта по ролям сайта внутри `auto_sync`, часы (по умолчанию 40; `0` — выключить) |
| `CHECK_ALL_DAYS` | глубина отчёта `/check_all` в днях (по умолчанию 14) |
| `ONLINE_MIN_HOURS` | минимальный недельный онлайн в часах для `/check_onlineall` и `/activity_week` (по умолчанию 9) |
| `HEALTH_CHECK_MINUTES` | период health-check (по умолчанию 15) |
| `DAILY_SUMMARY_HOUR` | час UTC ежедневной сводки (по умолчанию 9) |

Секреты (`CS2RED_*`, `STEAM_API_KEY`, `*_API_KEY`, `GITHUB_TOKEN`,
`DISCORD_TOKEN`) маскируются в логах и в `error_log.txt`.

## ИИ-агент (`quantum/agent.py`)

Наблюдатель за ботом, который пишет в служебный канал (`AGENT_CHANNEL_ID`):

- **ошибки команд** — сразу стильованным embed'ом «🚨 Ошибка в команде»;
- **утренний дайджест** — один раз в день после `AGENT_DIGEST_HOUR` (UTC):
  аптайм, пинг, заявки, голоса, модераторы, статус ИИ, правил, GitHub,
  cs2red и события аудита за последние сутки;
- **идея по улучшению** — раз в `AGENT_IDEA_INTERVAL_MINUTES`: ИИ-провайдера
  спрашивают напрямую (минуя RAG по правилам клана), ответ оформляется
  embed'ом «💡 Идея от ИИ-агента».

Периодических отчётов о состоянии больше нет — канал не забивается
одинаковыми сообщениями. Ошибки и проблемы health-check по-прежнему
приходят сразу. Последние 12 идей и дата последнего дайджеста хранятся в
таблице `meta`, поэтому после перезапуска агент не публикует всё пачкой.

## Команды

| Команда | Что делает |
|---|---|
| `/status` | профиль модератора: эффективность, разбивка по кланам, статус заявок и список активных заявок в работе, включая те, которые модератор взял кнопкой «Взять» (данные из таблицы `applications`). Ответ всегда ephemeral; чужую статистику видят только модераторы |
| `/admins` | кто администрирует клан: администраторы Discord, модераторы бота и ревьюерские роли (список кэшируется на минуту) |
| `/search` | история заявок игрока в клан: сводка (всего/принято/отклонено/в работе), разбивка по кланам и список заявок со статусом и `ticket-<message_id>`. Ответ всегда ephemeral; чужую историю видят только модераторы |
| `!setup_clan` (алиас `!setup`) | публикует в текущем канале официальные условия вступления (embed) и выпадающий список «Выберите клан» под ним — при выборе открывается модальное окно заявки. Текстовая команда, только для администраторов |
| `/check_mutes <steam_id>` | активные муты игрока на cs2red: тип, ник, причина, срок, дата и кто выдал. Если мутов нет — «✅ У игрока нет активных мутов». При 403/429 — «❌ Сайт cs2red временно недоступен» |
| `/check_bans <steam_id>` | активные баны и муты игрока на cs2red: тип, ник, причина, срок, даты блокировки/разблокировки и кто забанил. Если пусто — «✅ У игрока нет активных блокировок» |
| `/check [участник]` | все заявки, которые модератор когда-либо взял кнопкой «Взять»: активные и уже принятые/отклонённые, со статусом, заявителем, кланом и датой взятия. По умолчанию — свои; чужой список может посмотреть модератор. Ответ ephemeral |
| `/check_all` | баны и муты за `CHECK_ALL_DAYS` дней (по умолчанию 14) у всех участников с ролью TALENT: тип блокировки, дата, срок, причина и кто выдал. Ответ ephemeral, плюс мини-отчёт в лог-канал |
| `/check_onlineall` | недельный онлайн всех участников с ролью TALENT: для каждого берётся статистика из JSON-профиля cs2red (`user.Activity` — текущая и прошлая неделя, время наблюдателя). Кто наиграл меньше `ONLINE_MIN_HOURS` (по умолчанию 9 ч.) — выводится отдельным полем «⚠️ Малоактивные». Ник каждого игрока — ссылкой на профиль cs2red. Ответ ephemeral + итог в лог-канал |
| `/online` | кто из клана TALENT играет на серверах прямо сейчас: ник — ссылкой на профиль cs2red, рядом время на сервере. Источник — `/api/data/servers` (тот же, что у трекера активности), SteamID — из привязки `/link`. Ответ ephemeral |
| `/activity_week` | недельный отчёт по клану: топ активности, малоактивные ниже `ONLINE_MIN_HOURS` и отметка «🔴 2 недели подряд». Под отчётом — кнопки «Предупредить» (ЛС игроку) и «Снять роль»; снятие только вручную, автоматического нет. Ответ ephemeral |
| `/activity <steam_id>` | активность одного игрока по SteamID64: время и наблюдатель за текущую/прошлую неделю, рассмотрено репортов и разбивка по режимам. Ответ ephemeral |
| `/check_clan` | проверяет роли клана у всех привязанных через `/link`, а также у участников с ролью TALENT: у кого несколько ролей клана, у кого роль есть, но игрок не в клане, у кого в клане нет роли, кто без `/link`. Для непривязанных ищет профиль по Discord username; привязывает только при ровно одном результате. Отчёт ephemeral + кнопки «🔄 Синхронизировать роли» (снимает старые и выдаёт актуальные) и «🧹 Очистить лишние роли» (только для администраторов) |
| `/clan_info` | профиль клана одним embed: состав на cs2red, число участников с ролью, сколько без `/link`, сколько подтверждено в клане. Ответ ephemeral |
| `/health` | краткая публичная проверка: Discord, права, cs2red, ИИ, фоновые задачи и доступность служебных каналов. Без ID каналов, текстов ошибок и состояния БД |
| `/health_admin` | подробная диагностика: ID каналов, ошибки проверок, число записей в БД, провайдеры ИИ и последний HTTP-статус. Только администраторы, ответ ephemeral |
| `/moders` | панель модераторов: Discord-профиль, сколько прав выдано, приоритет (👑 полный / 🛡 высокий / 🔹 средний / 🔸 базовый / ⛔ без прав) и ссылка на профиль cs2red.ru, если SteamID привязан |
| `/give [участник]` | панель доступа: выбор участника, мульти-выбор команд, кнопки «💾 Сохранить», «➕ Все права» и «🧹 Очистить». После сохранения участник появляется в `/moders` и может пользоваться только отмеченными командами. Меню открывается только администраторам |
| `/take <участник>` | полностью забирает доступ модератора (удаляет из `/moders`) |
| `/audit [участник] [limit]` | журнал админских действий: кто, когда, что и над кем сделал, включая причины отказов по заявкам. `участник` фильтрует по тому, кто действовал или над кем действовали; `limit` — 1–50 записей. Только администраторы, ответ ephemeral |

Права модераторов хранятся в таблице `moderators` (колонка `commands`):
`["*"]` — все команды, пустой список — ни одной. Старые записи при
обновлении автоматически получают полный доступ. Проверка выполняется в
`MyBot.interaction_check`: администраторы Discord не ограничены, остальные
модераторы видят только разрешённые им команды.

### Роли клана

Бот не только выдаёт роль клана, но и **снимает** её, когда игрок выходит
из клана или переходит в другой: cs2red перестаёт показывать его в составе
`/api/clans`, и роль удаляется. Синхронизация запускается:

- каждые `SYNC_INTERVAL_MINUTES` минут (по умолчанию 15) — задача `auto_sync`;
- раз в час — задача `hourly_clan_sync`.

`auto_sync` уже обходит всех привязанных и синхронизирует роли сайта.
Раз в `SITE_ROLE_AUDIT_HOURS` часов (по умолчанию 40) он дополнительно
отправляет полный отчёт по этим ролям; отдельного обхода игроков нет.
Первый отчёт уходит при первом `auto_sync`, затем — по таймеру в `meta`.
Участники без `/link` в отчёте идут отдельно.

Прогресс обхода сохраняется в `meta` (`auto_sync_cursor`) при остановке на
`403/429`: следующий запуск продолжает с необработанных игроков, а не
начинает полный проход заново. Игрок, на котором сайт поставил лимит, не
считается обработанным и будет повторён. Для обычного прохода результаты
не сохраняются; после завершения прохода курсор очищается.

Каждый запуск пишет в лог-канал, **что именно изменилось** и какие роли
снять не удалось. Полная таблица «кто в каком клане» больше не публикуется
каждые 15 минут: она делала два лишних запроса на каждого игрока и могла
приводить к блокировке cs2red (429). Частые причины, по которым
автоматическое снятие не срабатывает:

- роль бота стоит **ниже** роли клана — Discord запрещает управлять такими
  ролями. В лог придёт список таких ролей; поднимите роль бота в настройках
  сервера выше ролей клана;
- у участника нет привязки `/link` — автоматика не знает его SteamID и
  пропускает; такие участники тоже перечисляются в отчёте;
- `GUILD_ID` не задан на Render — фоновые задачи не находят сервер.

Привязка запускается сама: при входе на сервер, при выдаче **любой** роли
(не только TALENT — например, «девушка»), кнопкой «Получить роль» и фоновым
обходом всех непривязанных раз в `AUTO_LINK_INTERVAL_HOURS` часов (первый
прогон — через 2–5 минут после старта). Ключ поиска — только Discord
username: если на cs2red он не совпадает с ником игрока или находится
несколько профилей, безопасно привязать нельзя — нужен `/link` или
`/admlink`.

Роли, созданные ботом, запоминаются в `clan_roles.json`, а выданная роль
конкретному участнику — в `clan_members.json` (оба в `DATA_DIR`), поэтому
роль снимется даже если клан переименовали или он исчез из `/api/clans`.

Роль клана, которую больше никто не носит, удаляется автоматически раз
в 10 часов (`CLAN_ROLE_CLEANUP_HOURS`) и сразу при выходе игрока из клана
или с сервера. Принудительно уборку запускает админ-команда
`/clan_roleclear`; служебные роли (BAN, модераторы и т.п.) не трогаются.

Роль снимается только по достоверным данным. Если cs2red не вернул поле
`roleId`, прислал незнакомый `roleId` (роль появилась на сайте, но её
названия бот не знает) или в ответе `/api/clans` игрока не оказалось,
роль остаётся на месте — иначе она пропадала бы «просто так». Роль клана
снимается только после `CLAN_ROLE_REMOVE_CONFIRMATIONS` проверок подряд
(по умолчанию 2, то есть два обхода автосинхронизации); как только игрок
снова находится в составе, счётчик обнуляется.

### История заявок

В таблице `applications` хранится только **последняя** заявка игрока
(`user_id` — PRIMARY KEY). Полная история ведётся в отдельной таблице
`application_history`: новая запись появляется при каждой подаче заявки
(уникальность — по паре `user_id` + `app_id`), а финальный статус
(принята/отклонена) и решитель дописываются при закрытии заявки.
Кто нажал «Взять», хранится в `taken_by`/`taken_at` обеих таблиц: `/status`
показывает такие активные заявки, `/check` — всю историю по модератору.
При первом запуске новой версии текущие заявки переносятся в историю
однократно (`INSERT OR IGNORE`).

## Безопасность

- HTTP-сессии разделены: админские cookie и заголовки `cs2red` уходят
  **только** на `cs2red.ru`. Steam, GitHub и LLM-провайдеры получают
  публичную сессию без cookie (`API.session` / `API.cs2red`).
- Хост определяется по hostname, а не по подстроке в URL.
- Панель управления (`/panel`) показывается только админу и только
  ephemeral-сообщением; каждая кнопка панели сама проверяет права.
- Голоса по заявке атомарны и привязаны к `app_id` заявки, а не к id
  сообщения: сообщение в канале и в ветке — одна запись голосов.
- Выбор клана в форме заявки отвечает модальным окном **первым** действием
  (Discord ждёт ответа 3 секунды — иначе «Приложение не ответило вовремя»,
  10062). View зарегистрирован как персистентный, поэтому опубликованное
  ранее сообщение со списком работает и после рестарта бота.
- Пустые или некорректные числовые переменные окружения не роняют бота на
  старте: значения читаются через `quantum.env.env_int` / `env_float`.

## Разработка и CI

```bash
pip install -r requirements.txt -r requirements-dev.txt
git config core.hooksPath .githooks   # один раз: pre-commit (ruff всегда, pytest при правках кода)
ruff check .
pytest                  # тесты + таблица покрытия по модулям (pytest-cov)
pytest --cov-report=term-missing   # то же, но с номерами непокрытых строк
docker compose config   # проверка compose-файла (нужен временный .env)
```

Правила работы с git — формат сообщений коммитов, включение хука, способы
откатить правки и почему JSON с данными игроков не версионируются — в
[`CONTRIBUTING.md`](CONTRIBUTING.md).

Покрытие считается только по коду бота (`--cov=quantum --cov=script`), тесты в
цифру не входят. Сейчас это ~49 % — подробности и самые «дырявые» модули
видны прямо в выводе `pytest`.

### Что делает CI (`.github/workflows/ci.yml`)

Запускается на `push` в `main`, `fix/**`, `feat/**`, на любом `pull_request` и
вручную (`workflow_dispatch`); параллельные прогоны одной ветки отменяют друг
друга (`concurrency`). Три job'а:

| Job | Что делает | Зачем |
|---|---|---|
| `test` | проверка пинов actions → Python 3.12 + зависимости → `ruff check .` → `pytest` с покрытием | ловит незакреплённые actions, ошибки импортов, неиспользуемый код и регрессии |
| `changes` | по `git diff` решает, тронуты ли только `*.md` и `docs/`, и отдаёт `docs_only` | не собирать образ на правках документации |
| `docker` | `docker compose config` → сборка через buildx с кэшем `type=gha` → smoke-запуск образа → проверка записи в `/data` на именованном volume | Dockerfile, compose и права тома проверяются на каждом пуше, а не в проде |

Детали, которые легко пропустить:

- **Проверка пинов** (`Check actions are pinned to commit SHA`) падает, если в
  `.github/workflows` появился `uses:` с тегом или веткой вместо 40-символьного
  commit SHA. Локальные actions (`./path`) разрешены.
- **`docker compose config`** запускается на временном `.env`, собранном из
  `.env.example` (только строки `KEY=VALUE`), поэтому ошибки в
  `docker-compose.yml` ловятся без настоящих секретов.
- **Smoke-тест образа** проверяет, что entrypoint отрабатывает без `/seed` и что
  `quantum.import_seed` и `script` импортируются внутри контейнера.
- **Проверка тома** запускает образ с именованным volume, убеждается, что
  процесс не root, `rules.txt` на месте, каталог доступен на запись (создаётся
  `quantum.db`) и запись переживает пересоздание контейнера.
- **`job docker` пропускается**, если изменения только в документации; ручной
  запуск (`workflow_dispatch`) собирает образ всегда.
- Все actions закреплены по commit SHA, обновляет их Dependabot
  (`.github/dependabot.yml`, раз в неделю).

## Release

Релиз запускается только после успешного CI. Workflow
`.github/workflows/release.yml` ждёт завершения `CI` на `main`, требует
approval environment `production` (если он настроен) и вызывает на
production-хосте `scripts/release.sh`. Скрипт сохраняет текущий образ
`quantum-bot:latest` как `quantum-bot:previous`, собирает новый, поднимает
compose и проверяет `/health`; при ошибке автоматически возвращает
предыдущий образ.

Секреты деплоя (`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`,
`DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, `HEALTH_URL`) задаются только в
GitHub Secrets. Подробная настройка, первый релиз и ручной откат — в
[`docs/RELEASE.md`](docs/RELEASE.md).

## Данные

Основное хранилище — SQLite (`quantum.db`, таблица `votes`, `applications`,
`links`, `players`, `users`, `moderators`, `seen`, `ai_cache`).
При первом запуске JSON-файлы (`links.json`, `players_db.json`,
`users_db.json`, `moderators.json`, `votes.json`, `seen.json`)
переносятся в SQLite и переименовываются в `*.bak`.
